# FETTA — BUILD MERCURY, THE HIGH-PERFORMANCE CODEBASE INGESTION ENGINE

We are now moving FETTA from visual prototype toward its real engineering foundation.

Your task is to build **MERCURY**.

Mercury is FETTA's deterministic, high-performance codebase ingestion, extraction, discovery, classification, and indexing subsystem.

This is an important architectural component.

Do not treat it as a normal "file upload feature."

---

# 0. THE FETTA ARCHITECTURE

FETTA is intended to become an AI engineering organization that can understand, remember, develop, pause, resume, and continue working on software projects over very long periods of time.

The conceptual architecture is:

```text
                         FETTA
                           │
             ┌─────────────┴─────────────┐
             │                           │
          MERCURY                    INTELLIMEM
       "What exists?"              "What do we know?"
             │                           │
      Deterministic facts        Persistent intelligence
             │                           │
             └─────────────┬─────────────┘
                           │
                      PROJECT BRAIN
                           │
                Specialist Engineering Agents
                           │
                      Coordinator
                           │
                       Execution
                           │
                      Verification
                           │
                      INTELLIMEM
```

These boundaries are fundamental.

## Mercury

Mercury answers:

> **What physically exists in this project right now?**

## IntelliMem

IntelliMem will answer:

> **What has FETTA learned, decided, verified, changed, rejected, and understood about this project over time?**

## Specialist agents

They will answer domain-specific questions:

> What does this mean from an architecture, backend, database, frontend, security, or testing perspective?

## Coordinator / Project Brain

It will eventually reason across all of this and decide what should happen next.

# 1. CRITICAL: MERCURY IS NOT AN AI AGENT

Do NOT use an LLM for Mercury's core work.

Mercury must be deterministic wherever deterministic computation is sufficient.

Do NOT use AI for:

* ZIP extraction
* file discovery
* directory traversal
* file classification
* hashing
* file metadata
* language detection where deterministic detection works
* ignore rules
* project statistics
* manifest detection
* package-manager detection
* dependency manifest parsing
* basic structural analysis
* basic imports/exports where reliable parsing is available

Do not spend tokens on work a filesystem/parser can perform faster and more reliably.

Mercury is systems engineering.

---

# 2. MERCURY'S PRIMARY OBJECTIVE

Mercury's fundamental objective is:

> **Make an imported codebase available to FETTA as quickly as technically possible, while producing a high-quality deterministic representation of that codebase.**

The target experience is:

```text
IMPORT
  ↓
MERCURY
  ↓
FAST INGESTION
  ↓
FAST EXTRACTION
  ↓
FAST DISCOVERY
  ↓
PARALLEL INDEXING
  ↓
PROGRESSIVE READINESS
  ↓
SPECIALIST AGENTS CAN BEGIN WORK
```

Do NOT design Mercury as:

```text
upload
→ wait
→ extract everything
→ wait
→ scan everything
→ wait
→ index everything
→ finally become usable
```

Instead design toward:

```text
stream
→ safely extract
→ discover immediately
→ classify
→ index in parallel
→ persist results
→ expose useful information progressively
→ continue secondary work in background
```

The goal is not merely fast completion.

The goal is:

> **How quickly can FETTA begin doing useful work?**

That is a first-class Mercury metric.

# 3. CURRENT INPUT: BROWSER ZIP

FETTA is currently browser-first.

Mercury v1 must support:

```text
Browser
   ↓
Repository ZIP
   ↓
Server-side ingestion
   ↓
Mercury
```

The browser must NOT individually upload tens of thousands of files.

Do not use:

```text
<input type="file" multiple>
```

as the core architecture for repository ingestion.

The repository should arrive as an archive and be processed server-side.

Avoid loading the entire archive into memory.

Use streaming/bounded-memory techniques where appropriate.

# 6. SECURE EXTRACTION

Treat every uploaded archive as untrusted.

Mercury must protect against:

### Path traversal

Reject or safely normalize entries such as:

```text
../../etc/passwd
```

and absolute paths.

### Malicious archives

Protect against:

* decompression bombs
* extreme compression ratios
* enormous expanded size
* excessive file counts
* pathological directory structures
* malformed archives
* invalid filenames
* unsafe symlinks

### Resource exhaustion

Use reasonable configurable limits for:

* archive size
* expanded size
* file count
* individual file size
* processing time where appropriate

Do not hard-code arbitrary tiny limits that make legitimate repositories unusable.

Make limits configurable.

### Code execution

NEVER execute repository code during ingestion.

Do not run:

```text
npm install
npm run
pnpm
yarn
pip install
cargo build
make
docker
shell scripts
```

or equivalent repository commands.

Mercury reads.

Mercury extracts.

Mercury indexes.

Mercury does NOT execute.

# 8. MERCURY'S FILE INDEX

Create a canonical machine-readable representation of discovered files.

Each indexed file should be able to expose useful deterministic metadata such as:

* stable file ID where appropriate
* relative path
* filename
* extension
* size
* content hash where useful
* language
* text/binary
* source/test/config/generated classification
* ignored status
* ignore reason if ignored
* relevant timestamps if available
* indexing status

Do not store enormous duplicated file contents inside metadata records unless required.

The source remains the source.

Indexes describe the source.

# 15. STRUCTURAL RELATIONSHIPS

---

# 16. HASHING + INCREMENTAL PROCESSING

Mercury must support efficient recognition of unchanged content.

Where useful:

```text

 ↓
content identity/hash
 ↓
compare with previous index
 ↓
unchanged → reuse
changed → reprocess
new → process
deleted → remove from current index
```

This becomes extremely important later when a developer returns to an existing project.

Mercury should eventually allow FETTA to answer:

> "What physically changed since the last time I saw this repository?"

Do not build an enormous distributed caching system.

Implement a clean, practical foundation.

Avoid throwing away already completed deterministic work.

Persist enough state to understand:

* current phase

Do not create an unnecessarily complicated distributed job system.

Keep v1 robust and understandable.

# 18. PROGRESSIVE READINESS

Mercury must distinguish between:

### Core readiness

Enough information exists for FETTA to begin understanding the project:

```text

+

+

+

+
project manifest persisted
```

### Secondary indexing

Additional work may continue afterward:

```text
deep structural relationships
additional metadata
language-specific analysis

```

This allows FETTA to begin useful work without waiting for every optional index.

Expose real status.

For example:

```text
UPLOADING
VALIDATING
EXTRACTING
DISCOVERING
INDEXING
READY
FAILED
```

Report actual progress where possible:

* bytes received
* files discovered
* files indexed
* files ignored
* current phase
* elapsed time
* throughput

Never fake progress.

# 23. INTELLIMEM MUST DISTINGUISH KNOWLEDGE TYPES

The future memory architecture must distinguish concepts such as:

### FACT

```text
PostgreSQL is used by the backend.
```

### OBSERVATION

```text
Appointment creation may have a concurrency issue.
```

### REQUIREMENT

```text
Appointments must never overlap.
```

### DECISION

```text
Use database-level protection for overlap prevention.
```

### REASON

```text
Application-only checking does not guarantee concurrency safety.
```

### VERIFICATION

```text
Concurrent creation was tested and the behavior was verified.
```

### REJECTED APPROACH

```text
Application-only checking was previously attempted and rejected.
```

These are different types of knowledge.

Do not collapse them into a single generic "memory" record.
